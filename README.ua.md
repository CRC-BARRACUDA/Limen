# Limen

*[English](README.md) · Українська*

**Модульний інструмент для безпеки, аналізу та аудиту.**

Limen — це модульний набір інструментів для безпеки, аналізу та аудиту:
портативне ядро, що перетворює невеликі вузькоспеціалізовані модулі на єдину
консоль. Замість одного монолітного інструмента ви складаєте *можливості*
(запити до кінцевих точок, системні операції, …), кожна з яких постачається
окремим модулем будь-якою зручною мовою.
Limen виявляє їх, посередничає у викликах між ними за єдиним контрактом, керує їх
встановленням і довірою з GitHub і відмальовує інтерфейс, який кожен модуль малює
для себе.

Простіше кажучи: Limen — це рушій, який збирає модулі в одному місці та дає їм
змогу взаємодіяти між собою.

---

## Що це

- **Портативність / спершу USB.** Базовий каталог застосунку — це власна тека
  виконуваного файлу (перевизначається через `$LIMEN_HOME`). Модулі, SDK,
  налаштування, сховище довіри та вбудовані інтерпретатори — усе лежить поряд із
  бінарником, ніщо не чіпає `~`.
- **Система модулів, два транспорти, один контракт.** Кожен модуль спілкується за
  тим самим контрактом JSON-RPC через один із:
  1. **stdio-підпроцес** (типово) — будь-яка мова (Python / JS / Lua / Go …)
     «просто працює»;
  2. **нативний C-ABI** (`libloading`, за згодою, довірений) — скомпільований
     `.so` / `.dll` / `.dylib` для Rust / C / Go.
- **Брокер можливостей.** Модулі оголошують можливості, які вони *надають* і
  *потребують*, у маніфесті `limen.toml`. Модуль викликає
  `host.call(capability, method, params)`, а ядро скеровує виклик до того модуля,
  що надає цю можливість. Ядро будує орієнтований граф залежностей за semver,
  топологічно сортує його й відхиляє цикли.
- **Менеджер пакетів на GitHub.** `limen-cli add owner/repo@version` читає маніфест із
  теґованого релізу, розв'язує граф залежностей між репозиторіями, завантажує,
  звіряє sha256-хеш із файлом блокування та встановлює. Нативні модулі
  підтягують готовий бінарник для платформи з активів релізу.
- **Дозволи та згода.** Маніфести оголошують чутливі дозволи (адміністратор,
  мережа, підпроцес, файлова система, привілейовані методи). Привілейовані методи
  запитують згоду під час виклику; надана довіра прив'язується до хешу в
  `trust.json`.
- **Самооновлення.** Під час запуску застосунок фоново перевіряє релізи на GitHub
  і пропонує оновлення просто в застосунку, якщо опубліковано новішу версію.
- **Багатомовний інтерфейс.** Застосунок доступний англійською та українською —
  мова береться з локалі ОС під час першого запуску й перемикається в
  налаштуваннях. Модулі перекладають власні вигляди через SDK, тож їхній текст
  слідує тому самому налаштуванню.

## Структура

```
src/
  limen-proto      контракт JSON-RPC + типи маніфесту
  limen-host       середовище виконання, завантажувач модулів, брокер можливостей, служби для модулів
  limen-core       рушій + домовленості на диску (шляхи, конфіг, налаштування, оновлення)
  limen-registry   менеджер пакетів GitHub (встановлення / блокування / довіра / перевірка)
  limen-cli        консольний інтерфейс      (бінарник: limen-cli)
  limen-gui        десктопний застосунок egui/eframe  (бінарник: Limen)
  limen-sdk-rust   Rust-SDK для модулів (разом із конструктором UI)
sdk/               впроваджувані SDK модулів для Python / JS / Lua
modules/           модулі першої сторони / демо (кожен — окремий git-репозиторій)
scripts/           пакування
```

Основні крейти тримають свої `.rs`-файли прямо в `src/<crate>/` (кожен `Cargo.toml`
задає явні шляхи `[lib]`/`[[bin]]`).

## Складання та запуск

Потрібен стабільний тулчейн Rust. Розробка ведеться на **debug**-збірках:

```bash
# GUI
cargo run -p limen-gui

# CLI
cargo run -p limen-cli -- <команда>
```

### Запуск без 3D-прискорювача

GUI малює своє вікно засобами OpenGL і потребує **версії 2.0 або новішої**. На
віртуальній машині, у віддаленому сеансі чи на ПК без 3D-драйвера Windows пропонує
лише програмний OpenGL 1.1 — тож `Limen` повідомляє, що не може запуститися, і
завершує роботу.

Щоб малювати програмно, завантажте `mesa3d-<версія>-release-msvc.7z` зі сторінки
[pal1000/mesa-dist-win](https://github.com/pal1000/mesa-dist-win/releases) і
скопіюйте ці три файли з теки `x64/` у ту саму теку, де лежить `Limen.exe`:

| Файл | Навіщо |
|---|---|
| `opengl32.dll` | точка входу драйвера, яку шукає Windows |
| `libgallium_wgl.dll` | сам рендерер (цей — ~59 МБ) |
| `dxil.dll` | компіляція шейдерів для типового Windows-драйвера Mesa |

Тоді Limen запускається нормально і все працює — рендеринг просто виконується на
CPU, тож він повільніший за справжній GPU. Потрібні всі три файли; без `dxil.dll`
застосунок падає без повідомлень.

> ⚠️ **Робіть це лише на машині без 3D-прискорення.** Ці файли *замінюють*
> системний драйвер OpenGL для того, що лежить поряд, тож якщо покласти їх біля
> `Limen.exe` на ПК зі справним GPU, це **вимкне** апаратне прискорення й
> сповільнить роботу.

`limen-cli` виконує ту саму роботу взагалі без GPU, і на нього це не впливає.

### Реліз + пакування

Обидва скрипти беруть версію з `[workspace.package]` у `Cargo.toml`, збирають
`Limen` + `limen-cli` у режимі release і пишуть у `dist/` для архітектури
машини, на якій відбувається складання.

**Linux**

```bash
./scripts/package-linux.sh
```

| Артефакт | Що |
|---|---|
| `Limen-<ver>-linux-<arch>.tar.gz` | Дистрибутивний тарбол — `Limen`, `limen-cli`, `LICENSE`, `JetBrainsMono-OFL.txt` (зі стрипнутими символами) |
| `Limen-<ver>-linux-<arch>.tar.gz.sha256` | Контрольна сума |

**Windows**

```powershell
.\scripts\package-windows.ps1
```

Потрібен 7-Zip (`winget install 7zip.7zip`) — у `PATH`, у типовому місці
встановлення або зареєстрований у `HKLM\SOFTWARE\7-Zip`. Кроку стрипу немає:
Windows тримає налагоджувальну інформацію в окремому `.pdb`, тож release-`.exe`
і так компактний.

| Артефакт | Що |
|---|---|
| `Limen-<ver>-windows-<arch>.7z` | Дистрибутивний архів — `Limen.exe`, `limen-cli.exe`, `LICENSE`, `JetBrainsMono-OFL.txt` |
| `Limen-<ver>-windows-<arch>.7z.sha256` | Контрольна сума |
| `Limen-<ver>-windows-<arch>.exe` | Сирий бінарник GUI, для самооновлення в застосунку |

> **Іменування активів релізу має значення.** Самооновлювач бере перший актив,
> чия назва містить **обидва** токени — ОС і архітектуру (`linux`/`windows`,
> `x86_64`/`aarch64`). Він віддає перевагу сирому бінарнику (перейменовує його
> прямо поверх запущеного виконуваного), інакше відкочується до архіву, з якого
> видобуває виконуваний файл (`.tar.gz` / `.tgz` / `.tar` / `.zip` / `.7z`).
> Зберігайте основу назви `<ver>-<os>-<arch>`: голий `Limen.exe` не має токенів
> і для оновлювача невидимий.

## CLI

```
limen-cli modules              перелік встановлених модулів та їхніх можливостей
limen-cli describe <cap>       самоопис постачальника можливості
limen-cli run <cap> <method>   виклик методу можливості (--params JSON, --target ID)
limen-cli add <ref>            встановити модуль і залежності (owner/repo[@версія] або локальний шлях)
limen-cli list                 перелік встановлених модулів із файлу блокування
limen-cli update [name]        перезавантажити й перевстановити модулі (усі або один за іменем)
limen-cli remove <name>        видалити модуль
limen-cli permissions          показати оголошені дозволи та стан довіри всіх модулів
limen-cli trust <name>         схвалити модуль (прив'язка до поточного хешу вмісту)
limen-cli untrust <name>       відкликати схвалення
limen-cli verify               sha256-перевірка встановлених модулів на підробку за файлом блокування
limen-cli demo                 запустити вбудоване крос-мовне, крос-транспортне демо
```

## Написання модуля

Модуль — це каталог із маніфестом `limen.toml` та точкою входу. Мінімальний
маніфест:

```toml
[module]
name = "local-devices"                # ідентифікатор, за яким його знаходять інші модулі
display_name = "Local Devices"        # гарна назва на картці (інакше — name)
description = "Enumerates locally attached devices."
tags = ["hardware", "inventory"]       # групування/фільтрування в менеджері модулів
version = "0.1.0"
language = "native"          # або "python" | "js" | "lua"
entry = "local_devices"      # точка входу: бінарник/скрипт/бібліотека
abi = "rpc"                  # rpc (типово, через stdio) | native (внутрішньопроцесний C-ABI)
repo = "CRC-BARRACUDA/limen-local-devices"

[provides]
capabilities = ["devices.local"]

[permissions]
subprocess = true
```

`display_name` і `description` — це те, що показує картка модуля, як у переліку
встановлених, так і в переліку доступних. `tags` відображаються на картці як
клікабельні `#чипи` — клік фільтрує перелік за тегом, і теги також враховує
пошук. Обидва є **англійськими типовими**
значеннями — додайте поряд із маніфестом `locales/<lang>.toml` із `[module]
title` / `description`, щоб перевизначити їх для кожної мови:

```toml
# locales/uk.toml
[module]
title = "Локальні пристрої"
description = "Перелічує локально під'єднані пристрої."
```

Модулям впроваджується SDK під час запуску (Python / JS / Lua) або вони лінкують
Rust-SDK. Усі надають однаковий інтерфейс — `host.call` / `emit` / `subscribe` /
`about` / `log` — плюс конструктор UI (`Window` / `Label` / `Text` / `Select` /
`Button` / `Row` / `Separator` / `Table`), чию повернуту специфікацію вигляду
відмальовує GUI. Модуль, що малює власний інтерфейс, повертає цю специфікацію з
методу `ui`; дії, що повертають нову специфікацію вигляду, перемальовуються на
місці.

Модулі розповсюджуються як власні репозиторії GitHub
(`CRC-BARRACUDA/limen-<name>`) і **не** є частиною цього робочого простору.
